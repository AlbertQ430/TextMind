# TextMind 已确认的需求共识

> 状态：需求探索阶段的阶段性记录。本文只记录已经达成共识的内容，不代表 SRS 已冻结。

## 1. 产品定位

TextMind 是本地优先的个人知识管理与 AI 辅助学习系统，以知识库为中心，而不是以聊天记录或单篇文档为中心。

项目包含两个主要模块：
- **知识管理工作台**：日常资料管理、检索和 AI 知识加工。
- **检索实验室**：数据集、算法配置、实验运行、指标评估和结果比较。

两者共用底层检索实现，但实验室的实验索引、配置和结果与日常工作台隔离。核心工作流为“文档 → 检索 → AI 加工 → Markdown 成果 → 再利用”。

## 2. 知识库组织

- 支持多个独立知识库；一个知识库对应文件系统中的一个真实目录。
- 支持新建知识库和打开已有目录。
- 已有目录可初始化为知识库；如果已有 `.textmind/`，读取元数据并恢复原知识库。
- 同一个目录重复打开时应识别为同一个知识库。
- 多个知识库完全独立，不共享知识库数据，不跨库检索，不建立跨库链接或统一索引。
- 全局模型配置可以共享，但不因此形成知识库数据关联。
- 用户目录是知识库载体；`.textmind/` 保存内部状态，例如元数据、索引和缓存。
- 原始文本文件是事实来源，数据库、元数据和索引属于可重建的派生数据。
- 如果 `.textmind/` 存在但损坏，应进入修复或重建流程，而不是直接当作新知识库。

## 3. 文件管理与同步

- 采用导入式管理：导入时将文件复制到知识库目录，知识库中的副本成为工作副本。
- 用户可以通过 Finder、VS Code 等外部工具直接修改知识库文件。
- TextMind 只做轻量文件管理，不定位为完整文本编辑器；文件浏览、导入、目录管理、检索片段预览和原文定位有价值。
- 不采用实时文件监听。每次打开程序或知识库时检查变化，并支持手动同步。
- 采用增量同步：
  - 新增：解析并建立索引。
  - 修改：重新解析、分块和索引。
  - 重命名或移动：更新路径及关联信息。
  - 删除：删除对应索引和元数据。
  - 未变化：不重复处理。
  - 索引损坏：根据原始文件重建。
- 移除或重置知识库数据时，只删除 `.textmind/` 内部数据，不删除用户文件和 AI 成果。重新打开目录时可以重新初始化索引。界面文案应避免让用户误以为整个目录会被删除。

## 4. 文件格式与知识成果

### 4.1 输入格式

- 首版支持 TXT 和 Markdown。
- 知识库内部只保存纯文本笔记。
- 导入 TXT、Markdown 时原样复制，不主动改写或统一重写。
- 未来扩展 PDF、EPUB、DOCX 等格式时，进入知识库前也需要转换为纯文本笔记。
- 原文提取与 AI 总结性质不同，未来扩展格式时应区分来源，不能把 AI 总结冒充原文。

### 4.2 AI 成果

- AI 生成成果统一使用 Markdown，保存在当前知识库的 `AI_note/` 目录。
- AI 成果与原始笔记分开保存，不自动覆盖原始文件。
- 使用普通 Markdown 语法，尽量可移植，不依赖 TextMind 专有格式；尽可能保留来源信息和相对路径引用。
- AI 成果可以参与知识库检索，但用户可以控制是否纳入。
- 原始来源文件删除后，AI 成果仍然保留；失效引用标记来源文件已删除，不自动删除成果。
- AI 成果是独立、可长期保存和再次加工的知识对象，不依赖聊天记录存在。
- 首版不保留多轮对话历史。
- AI 任务生成的成果直接保存为独立文件，不要求额外确认；用户不满意时可以自行删除。
- 可使用 `original` 和 `ai_generated` 等来源类型元数据区分原始资料与 AI 生成资料。

## 5. AI 知识加工

- AI 采用用户主动发起的方式，不擅自扫描或处理整个知识库。
- 任务输入方式包括：
  1. 单文档处理：总结、提取知识点、生成复习提纲等。
  2. 多文档处理：综合总结、内容比较、观点归纳等。
  3. 检索结果处理：基于检索内容生成问答或主题归纳。
- 任务形式采用内置任务 + 自定义任务。内置任务包括总结、知识点提取、文档比较、复习提纲、复习题生成和知识库问答等。
- 首版自定义任务只需自然语言指令输入，不开发复杂模板编辑器。
- 知识库问答优先依据检索结果回答，并提供原文出处。出处至少包含文档名称和具体内容位置（如 Markdown 标题或原文片段），并支持定位原文。

## 6. 检索系统

- 使用统一检索管线支持多种算法。
- 首版优先考虑 BM25、Dense Search 和 Hybrid Search。
- BM25 作为关键词检索基线；Dense Search 提供语义检索；Hybrid Search 是重点研究和改进方向。
- Hybrid 初步考虑 BM25 + Dense Search + RRF（倒数排名融合）。
- Reranker 后置，不作为首版重点。
- 不同检索算法共用统一文本处理和 Chunk 数据；检索结果统一包含文档、Chunk、相关性分数和来源位置等信息。
- 检索实验室与工作台共用底层检索服务，但实验室可以独立调整算法、参数和模型。
- 实验室实验索引独立，不得修改工作台日常索引或检索配置。

## 7. 文本解析与分块

- Markdown 优先按标题层级分块。
- 无标题 Markdown 和 TXT 按段落分块；超长章节可再按段落递归拆分。
- 首版不要求复杂短块合并策略。
- 保留标题路径、来源文件和原文位置等元数据。
- 原始文本保持不变；Chunk 正文独立保存，标题路径作为元数据，可作为检索辅助上下文。
- Chunk 长度提供系统默认值，并允许通过高级设置调整。

## 8. 配置管理

- 支持全局检索配置。
- 优先考虑知识库级配置覆盖全局配置。
- 全局模型配置尽量统一，不要求每个知识库分别配置一套模型。
- 检索实验室可将合适配置应用到工作台；应用配置不修改历史实验记录。
- 全局配置与知识库覆盖机制是否在首版完整实现，仍需评估。

## 9. 实验结果与耗时统计

核心评价指标已确定为 Precision@K、Recall@K、MRR、NDCG@K 和检索耗时。

耗时统计采用端到端检索耗时：
- 模型加载时间单独记录，不计入检索耗时。
- 索引构建时间单独记录，不计入检索耗时。
- 正式计时前进行预热。
- 每条 Query 重复执行 3 次，记录平均耗时和中位耗时。
- 同一批实验尽可能复用已加载的模型实例。
- 不将 LLM 生成回答的时间计入检索耗时。

结果展示倾向于每个指标独立使用柱状图比较不同检索配置，同时提供精确数值表和按需查看的单条 Query 详情。
