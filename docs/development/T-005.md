## 1. 任务定义

### 1.1 目标

实现结果目录与终态发布链路：把单变体执行结果转换为正式运行记录，生成单运行图表，在 staging 目录完成原子发布，并在服务重启时使用合法 JSON 与 SQLite 状态进行幂等对齐。

### 1.2 范围

包含：

- `RunRecordPublisher`，实现 T-004 的 TerminalPublisher 接口。
- `results/runs` 的 staging 目录、原子目录发布和记录读取。
- Completed、Failed、Cancelled、Interrupted 四类终态记录。
- 单运行指标图和计时图。
- 最小 Interrupted 记录。
- SQLite 活跃任务与规范 JSON 的重启对齐。
- 合法 staging 记录在重启时优先发布。
- 记录写入、图表失败和 SQLite 提交失败的错误边界。

不包含：

- preload result 构建。
- JSON 导入、历史列表、比较或 Web。
- 跨运行图表。
- 删除记录或恢复用户删除的文件。
- 预置结果目录与 imports 目录的完整管理。

## 2. 结果目录

规范目录：

```text
results/runs/<run_id>/
  run.json
  charts/
    metrics.png
    timing.png
```

staging：

```text
results/runs/.staging/<run_id>-<attempt_id>/
```

- staging 目录只能用于一次发布尝试。
- 整个 staging 目录通过目录重命名发布为最终目录。
- 最终目录已存在时不得覆盖。
- 合法最终记录优先于 staging。
- 结果来源由目录决定，JSON 不保存 source/import_time。

## 3. TerminalPublisher 扩展

为 T-004 增加只读恢复能力：

```python
class ResultReconciler(Protocol):
    def reconcile(self, task: TaskRecord) -> RecoveryResult | None: ...
```

`RecoveryResult` 至少包含：

- `status`
- `ended_at`
- 可选 `cancelled_at`

行为：

- 规范 JSON 存在且有效：返回 JSON 中的终态，TaskService 用其对齐 SQLite。
- 规范 JSON 不存在但唯一合法 staging 记录存在：先原子发布，再返回终态。
- 没有可恢复记录：返回 `None`，TaskService 生成最小 Interrupted 记录。
- 多个合法 staging 候选：记录冲突错误，不自动选择。

TerminalPublisher 的发布方法与 reconciler 可由同一 `RunRecordPublisher` 实现。

## 4. 终态记录组装

### 4.1 Completed

从 `TaskRecord` 与 `ExecutionResult` 组装：

- `format_version="1.0"`
- Run/Plan/Variant 标识
- plan/variant 名称快照
- `status="Completed"`
- 数据集与实际执行配置
- metrics、query coverage、14 项 timing
- environment
- stage progress
- 成功图表列表
- `error=None`

记录必须通过 T-002 `RunRecord` 校验。

### 4.2 Failed

- 状态 `Failed`
- 保留已完成阶段、当前/失败阶段和错误摘要
- `metrics=None`，不得伪造
- timing 可使用可获得的已记录值；不可得时为 `null`
- charts 可为空

### 4.3 Cancelled

- 状态 `Cancelled`
- 必须包含 `cancelled_at`
- 保留取消请求所在阶段和已完成阶段
- metrics 可为空

### 4.4 Interrupted

最小记录必须包含：

- Run/Plan/Variant 标识和名称
- 配置快照
- started/finished 时间
- dataset 标识与划分；未知计数为 null
- stage progress
- timing 全 null
- environment 空对象或已有值
- charts 空数组
- `error.message` 说明服务中断

### 4.5 禁止字段

JSON 不得出现：

- `source`
- `result_source`
- `import_time`

## 5. 图表

正常 Completed 运行生成：

- `charts/metrics.png`
- `charts/timing.png`

要求：

- 只使用当前变体数据。
- 先写临时文件，再原子改名。
- 图表生成失败不改变 Completed 状态。
- 只有实际成功且存在的图表进入 `charts`。
- 图表路径为相对 POSIX 路径。
- 图表不得引用其他运行或全局课程汇总数据。

## 6. 发布流程

完成路径：

1. 生成图表到独立 staging 目录。
2. 基于成功图表组装 Completed 记录。
3. 使用 RunRecord 校验。
4. 校验图表路径存在且不越界。
5. 原子发布整个 staging 目录。
6. 返回发布成功。
7. TaskService 随后更新 SQLite 终态。

失败、取消和中断路径遵循相同 staging → 发布 → SQLite 顺序。

如果 JSON 发布成功但 SQLite 更新失败，结果 JSON 保留，任务非终态；重启时由 reconciler 对齐。

## 7. 恢复

服务启动恢复顺序：

1. T-004 清空 Pending 并创建 notice。
2. 对每个遗留活跃任务查询最终记录。
3. 最终记录有效：按 JSON 状态对齐 SQLite，不重新执行、不覆盖记录。
4. 最终记录缺失、唯一 staging 记录有效：发布 staging，再按 JSON 对齐。
5. 没有合法记录：生成最小 Interrupted 记录并提交 SQLite。
6. 记录损坏或 staging 冲突：保留非终态/失败证据，不伪造 Completed。
7. 恢复幂等，重复启动不重复发布。

#### 接口实现

- `ResultRepository`：默认根目录 `results/runs`；staging 位于 `.staging/<run_id>-<attempt_id>`，每次发布创建独立目录；`publish()` 使用 `os.rename` 整体原子发布，最终目录已存在时抛 `ResultConflictError` 且不覆盖；`write_record()` 先 `parse_run_record` 校验，再写 `run.json.tmp` 并原子替换；`read()/read_at()` 对损坏记录抛 `ResultRecordError`；`find_staging_candidates()` 仅匹配 `<run_id>-` 前缀；`validate_chart_paths()` 要求图表为目录内相对 POSIX 路径且文件存在；Run ID 非法或路径越界抛 `ResultPathError`。
- `charts.generate_charts()`：使用 `Figure` + `FigureCanvasAgg`（不依赖 pyplot 全局状态），只绘制当前变体的 metrics 与适用 timing；先写 `.tmp-*` 并确认可读，再 `os.replace`；单图异常记录日志并返回空清单；标题包含方案、变体和模型名称。
- `RunRecordPublisher`：
  - `publish_completed()`：staging → 图表 → 组装 → `write_record` 校验 → 图表路径校验 → 原子发布。
  - `publish_failed()/publish_cancelled()/publish_interrupted()`：最小化组装，timing 全 `null`、`metrics=null`、`charts=[]`，Cancelled 必含 `cancelled_at`，Interrupted 使用 `SERVICE_INTERRUPTED` 详情。
  - `reconcile()`：最终 JSON 有效时直接返回终态；无最终记录时扫描 staging，唯一合法候选先原子发布再返回；多个合法候选抛 `ResultConflictError`；损坏的最终记录抛 `ResultRecordError`，损坏的 staging 候选被忽略。
- `TaskService`：`reconciler` 为可选关键字参数；恢复时逐任务调用 `reconcile()`，成功则按 JSON 的 `status/ended_at` 对齐 SQLite；异常时写入 `error_summary` 并保留非终态；无记录时走原有最小 Interrupted 发布。未传 `reconciler` 时保持 T-004 行为。
- 记录内容：不写入 `source`、`result_source`、`import_time`；来源由目录决定；图表清单只包含实际成功且已存在的文件。

#### 风险与遗留项

- 风险：若 SQLite 状态与 JSON 终态之间的转换不在状态机允许范围内（例如 `Cancelling -> Completed`），恢复会记录“恢复对齐失败”并保留非终态，不强制覆盖；需要后续任务明确该极端场景的处理策略。

#### 接口实现

- 身份校验：`_identity_matches(record, task)` 要求四个标识完全一致；最终记录不匹配时抛 `ResultRecordError`，staging 候选不匹配时跳过，不参与对齐。
- 终态对齐：`_force_terminal(run_id, status, ended_at, error_summary)` 使用 `BEGIN IMMEDIATE` + 条件 `UPDATE ... WHERE status IN (Preparing, Running, Cancelling)`，仅用于启动恢复；正常运行仍走 `transition` 状态机。
- 恢复分支：
  - 合法记录（身份一致）→ `_force_terminal` 按 JSON 终态和时间对齐。
  - 多个合法 staging → `_interrupt_or_force` 发布最小 Interrupted 记录（原候选保留），失败时仅强制 SQLite 终态。
  - 损坏最终记录或身份不符 → `_force_terminal(Interrupted)`，保留损坏文件，`error_summary` 记录“恢复对齐失败”。
  - 无任何记录 → 原有最小 Interrupted 发布流程。
- 幂等：任务已终态时不再进入 `active_tasks()`，重复启动不重复发布或改写记录。
